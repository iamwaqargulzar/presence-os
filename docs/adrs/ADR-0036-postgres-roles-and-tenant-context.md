# ADR-0036 — PostgreSQL Roles, Tenant Context and Forced RLS
Status: Accepted (2026-11-25). Made during R0-003 under the owner's delegation in ADR-0032 and ADR-0033. Independent review of the role and policy migrations is pending.

## Context
R0-003 must separate the migration and runtime roles, set tenant context so a reused connection cannot leak it, decide where FORCE ROW LEVEL SECURITY applies, and stop foreign-key checks from crossing tenants. ADR-0004 and ADR-0033 fix the baseline: shared database, `tenant_id`, RLS, transaction-scoped context, no external pooler at the start.

## Decision
1. **Three roles.** The bootstrap superuser from `compose.yaml` only creates roles (`infra/postgres/roles.sh`). `presence_migrator` owns the schema and is the Django `migrator` alias. `presence_app` is the `default` alias: owns nothing, no BYPASSRLS, NOINHERIT, no TRUNCATE. Two passwords, `PRESENCE_DB_MIGRATOR_PASSWORD` and `PRESENCE_DB_APP_PASSWORD`.
2. **Context.** `tenant_context()` runs `set_config('presence.tenant_id', …, true)` inside `transaction.atomic`. Policies compare `tenant_id` with `NULLIF(current_setting(..., true), '')::uuid`, so a missing context matches nothing.
3. **FORCE on every tenant table.** No per-table exceptions without a new ADR. Data migrations therefore set a tenant context too.
4. **Composite foreign keys.** Tenant tables reference each other through `(tenant_id, id)`, because foreign-key checks ignore RLS.
5. **Detection.** A test lists every public table with a `tenant_id` column that lacks enabled and forced RLS or a policy.
6. **Tests commit real rows** (`SimpleTestCase`, not `TestCase`), so each tenant context is a real transaction, as in production.

## Alternatives considered
- Session-scoped `SET presence.tenant_id`: leaks through pooled connections. Rejected by ADR-0033.
- FORCE only on selected tables: the owner role runs migrations and could silently read or write across tenants. Uniform FORCE is simpler to check.
- A trigger that checks parent tenant: more code than a composite key, and the plain foreign key would still leak existence.
- Policies generated by a third-party library: a dependency for three SQL statements.

## Consequences
- Every query on a tenant table needs `tenant_context()`; forgetting it returns nothing rather than leaking.
- `presence_migrator` has CREATEDB in development and CI only; production provisioning (R0-007/R0-008) must create it without CREATEDB.
- Tables created before migration 0001 are not granted to `presence_app`.

## Security impact
Isolation is enforced by the database for both roles. The runtime role cannot change policies, truncate, or bypass RLS.

## Cost/operational impact
Two extra statements per transaction. `make services-up` reapplies roles and passwords each run.

## Migration / rollback
`manage.py migrate presence_core zero --database migrator` reverses migration 0001 (tested in CI). Roles stay until removed by hand or with `docker compose down -v` locally.
